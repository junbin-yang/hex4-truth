> 评审对象: 深开鸿十大 KaihongOS 关键技术难题之课题 4

## 1. 课题 4 需求解析

课题 4 要求安全能力从"外部附加拦截"转变为"**Agent 本体理解的内在约束**"。
本体是对业务世界的确定性建模, 含语义/状态/行为三层结构, 物理约束作为第四层内建其中:

| 层 | 课题要求 | 关键词 |
|---|---|---|
| 语义层 | 实体可访问性/关系可遍历性/属性可读性作为 Schema 一等公民, 本体到工具编译, 越权查询在知识库访问阶段即被拒绝 | 本体→工具编译 |
| 状态层 | 基于任务上下文与调用者身份的最小权限数据访问, 未授权数据对 Agent 不可见, 在 MCP 层之前完成拦截 | 最小权限 |
| 行为层 | 每个动作执行"主体权限＋前置条件＋参数合法性"**确定性三元校验**, 不依赖 LLM 概率判断 | 确定性校验 |
| 物理约束层 | 物理约束规范(ISO 10218、ISO 13482 等)形式化为 SMT/LTL 规则内建到本体, 确定性安全监控器超限即否决 | 形式化+监控器 |

达成效果指标:

1. 提示注入导致的隐私泄露/数据越权/错误操作拒绝率 ≥ 99.9%
2. 任务劫持/控制流劫持/越权下发攻击拒绝率 ≥ 99%
3. 未授权数据查询在规划阶段拦截率 ≥ 99%, 误报率 ≤ 1%
4. 物理动作类高危指令(速度/距离/力超限)实时拦截率 ≥ 99%, 端到端延迟 ≤ 20 ms
5. 物理安全约束形式化覆盖率 ≥ 90%, 形式化规约正确性验证通过率 100%

## 2. 现有能力盘点

### 2.1 mclaw — 深开鸿 AI Agent Runtime(上位机侧)

`third_party/mclaw`(Apache-2.0, 深开鸿出品), 提供完整的"规划→调度→执行"链路:

- **Agent 执行循环**: `mclaw/agent/core.py`(3000+ 行)统一驱动模型推理、工具编排与会话状态;
- **工具注册与派发**: `mclaw/tools/registry.py` + `dispatch.py`,
  其中 `dispatch.py:681` 已有 safety preflight 挂钩点(`MClawSafetyLayer.plan()`);
- **物理世界执行入口**: `mclaw/skills/kaihong-robot-dog/` 经 HTTP 控制深开鸿机器狗
  (移动/转向/动作序列), 即课题所述"执行端触及物理世界"的现成链路;
- **平台适配**: 支持 Linux / Kaihong OS / M-Robots OS(`mclaw/runtime/kaihong.py`)。

现有 safety 层(`mclaw/safety/`)仅覆盖文件域安全: PathPolicy 路径策略、
Scoped Secret 凭据隔离、Checkpoint/Rollback 文件快照回滚。
**README 自认缺陷: "M-Claw 1.0.0 不提供安全沙箱或权限分级"** —— 这正是课题 4 要补的能力。
无 MCP 层、无知识库/本体/知识图谱模块。

### 2.2 hex4_guard — 确定性安全监控器(设备侧)

`esp32s3_hex4_guard/`(板级实测完成, 详见
[`ESP32-S3安全监控器设计文档.md`](ESP32-S3安全监控器设计文档.md)), 与本课题直接对应的能力:

- **行为层**: L3 判定 = 角色权限位掩码 + 参数形状(RANGE/ENUM/RANGE_LUT/COND)
  + 动作级门控(when→deny) + 状态机前置 —— "主体权限＋前置条件＋参数合法性"
  确定性三元校验的现成实现, 设备端纯查表、无 LLM 参与;
- **物理约束层**: ISO 条款 DSL(`tools/iso_constraints/*.yaml`, 形状封闭集
  range/enum/combine2/when/ltl) → z3 四项验证 + LTL BMC → C 规则表/转移表生成;
  场景 A 覆盖率 9/9 = 100%(`docs/iso_clause_matrix.md`), 验证全 PASS 才允许生成;
- **状态层**: 表驱动安全状态机(deny 位图、E-STOP 确认重启闭环、断线自动锁存);
- **确定性时延**: 设备判定实测 877~1338 µs(JSON+HMAC+全判定层+回执),
  课题 4 指标要求 ≤ 20 ms, 余量约 17 倍;
- **本体层防篡改**: 规则表编译期固化 flash + Flash Encryption + RD_DIS 威胁模型
  (设计文档 §8.6), 回应课题难点"保证本体层本身不被篡改";
- **链路安全**: 帧 CRC + 角色密钥 HMAC-SHA256 + 防重放滑动窗口 + 断线安全停止。

## 3. 课题 4 指标逐条映射

| 指标 | 现有能力承接 | 差距 |
|---|---|---|
| ① 提示注入拒绝率 ≥99.9% | 行为层确定性校验不依赖 LLM, 注入产生的越权指令在 guard 处必然拒绝 | 需在 mclaw 侧新增规划阶段约束校验, 并建立提示注入红队测试集与拒绝率统计框架 |
| ② 任务/控制流劫持拒绝率 ≥99% | guard 安全状态机(仅合法转移路径可达) + 帧 HMAC 验签 + 防重放, 已板级实测 | 需打通 mclaw→guard 协议链路, 将"任务"映射为状态机事件 |
| ③ 未授权查询规划阶段拦截 ≥99%、误报 ≤1% | **无** —— 两项目均无本体/知识库能力 | **最大差距**: 需新建语义层(本体 Schema + 本体→工具编译)与状态层(最小权限数据可见性) |
| ④ 物理动作实时拦截 ≥99%、≤20ms | **已达标**: 设备判定 877~1338 µs 实测, ULP 传感器包络并行值守(0 抖动) | 需补 UART 链路端到端实测(115200 波特率下 ~50B 帧传输约 5 ms, 预算可行) |
| ⑤ 形式化覆盖率 ≥90%、验证通过率 100% | **已达标**: 工具链自动统计覆盖率(场景 A 口径 9/9=100%), z3 全 PASS 才生成规则表 | 扩展场景时按 `iso_clause_matrix.md` 逐条核定标准原文数值(文档已诚实标注演示取值非标准原文) |

## 4. 推荐架构

本体四层跨两级部署: 语义/状态层在 Agent 侧(信息世界), 行为/物理约束层在设备侧
(物理世界) —— 与课题"本体内建"而非"外部拦截"的定位一致:

```
mclaw(上位机, RK3588/Kaihong OS)                    hex4_guard(设备侧, ESP32-S3)
┌──────────────────────────────────┐   UART      ┌──────────────────────────────────┐
│ 本体四层 — 待新建①②, 接入③④      │            │ 本体四层 — 已有③④                │
│ ① 语义层: Ontology 模块          │ guard_cmd  │ ③ 行为层: L3 三元校验(权限+前置  │
│    实体/关系/属性 Schema 一等公民 │  协议下发   │    条件+参数形状, 纯查表确定性)  │
│    本体→工具 Schema 编译         │ (HMAC 帧,  │ ④ 物理约束层: z3 验证过的规则表  │
│    越权查询在知识库阶段即拒绝    │  防重放)    │    + 表驱动安全状态机            │
│ ② 状态层: dispatch preflight     │───────────►│ ULP 传感器包络并行值守(0 抖动)   │
│    任务上下文×身份最小权限       │            │ 规则表固化 flash(防本体篡改)      │
│    未授权数据不进 Agent 上下文   │            │ 判定实测 877~1338µs(<20ms 预算)  │
└──────────────────────────────────┘            └──────────────────────────────────┘
```

改造点:

1. **mclaw 侧(工作量主体)**: 语义层本体引擎(本体建模 → 工具 Schema 编译)与状态层
   访问控制, 挂在 `dispatch.py` 既有 safety preflight 挂钩点; 机器人 skill 的下发命令
   改走 `tools/guard_cmd.py` 协议(经 UART 至 hex4_guard), 代替当前直连 HTTP;
2. **hex4_guard 侧(小)**: 动作表接入机器狗动作域(speed/force 参数与现有五参数协议
   天然对应), 状态机事件集对接任务生命周期;
3. **形式化反馈闭环**: z3 验证结果(如 deny 原因、约束修正建议)经回执反馈到 mclaw
   规划循环 —— 回应课题技术难点"如何将形式化验证结果反馈到 Agent 规划循环"。

## 5. 差距、风险与工作量

| 项 | 说明 | 量级 |
|---|---|---|
| 语义层本体引擎 | 全新开发; 本体建模语言选型(OWL/RDF 或轻量 DSL)与"本体→工具编译"是课题核心创新点, 也是最大不确定性 | 大 |
| 状态层最小权限 | 需引入数据可见性控制(在 MCP 层之前拦截; mclaw 当前无 MCP, 可自建等价层或引入 MCP 服务) | 中 |
| 指标①②③量化验证 | 需要提示注入/劫持攻击红队测试集、拦截率与误报率统计框架 —— 工作量而非技术不可行 | 中 |
| 端到端 ≤20ms 链路 | 设备侧已实测达标; UART 传输与上位机协议处理需补链路级实测 | 小 |
| ISO 数值核定 | 正式申报前须对照 ISO 10218/TS 15066 原文替换演示取值(见 `iso_clause_matrix.md` §4 诚实性承诺) | 小 |
| mclaw 版本依赖 | mclaw 处于快速迭代(1.0.0, 源码安装); 集成方案应以插件形式存在, 避免深度 fork | 中 |
